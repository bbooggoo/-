# 제원 질의 데스크 — 사내 특허 통합 제안서 v5

작성일: 2026-10-22 | 수정: 설비·UT 변경 정의 및 질의 수정분 중복 인식 방지 설계 추가

사용자 답변에 따라 추가·삭제·변경의 정의, BULK 변경의 즉시 반영, 복원 가능한 이력 및 최종 제원 확인 절차를 정리하였다. 2026-10-22 공개 선행특허·문헌 1차 조사 내용을 16~17절에 추가하였다. 정식 선행기술 조사와 출원용 검토는 미완료이며 운영 효과는 아직 실측 전이다. 이전 버전에서 별도 결재본 보관을 전제로 한 부분은 본 문서의 정의로 수정한다.

## 1. 발명의 명칭

**동일 유형 질의의 통합 처리 및 변경 이력 연계를 이용한 반도체 설비 제원 데이터 관리 방법 및 시스템**

## 2. 발명의 핵심

제원 항목과 질의·답변·수정 이력을 DB로 연결하고, 동일 유형의 질의를 대공정별로 묶어 처리하여 반복적인 질의 왕복을 줄인다. 특정 시점의 제원에 대해 대공정 기술팀 담당자의 최종 확인 이력을 남기고, 후속 BULK 변경 제원은 접수 즉시 현재 DB에 반영한다. 이전 상태로 돌아가 수정할 수 있는 이력을 이용해 변경 전후 제원을 추적한다.

변경자료는 추가·삭제·수정이 표시된 PJT 전체본과 표시 없는 PJT 전체본으로 구분한다. 표시 없는 전체본은 기존 PJT DB와 건설코드 및 제원값을 비교하여 추가·삭제·변경을 식별한다. 제원량 증감을 산출하고 수십~수백 대에 걸친 변경을 현재 DB에 반영한다.

핵심은 ‘질의 결과가 반영된 현재 제원을 DB로 확인하고, BULK 변경 전후의 제원과 담당자 확인 이력을 연결하는 것’이다. 이력 학습에 따른 자동변환과 자동설계는 향후 개발이다.

## 3. 현행 업무와 규모

제원 접수 후 설계사의 최초 검토에 약 1주가 소요된다. 이후 PPT 질의 패키지를 발행하고 제조 기술팀과 답변을 주고받으며, 패키지당 최소 5근무일 이상의 왕복 및 재질의가 발생한다. 프로젝트당 약 10회 이상 패키지가 발행되고 최초 검토 1주와 별도로 질의·검토 과정에 약 2개월이 소요된다.

대표 규모는 프로젝트당 설비 약 1,500대, 개별 질의 약 300~400건 예상이다. 참여자는 설계사·협력사 약 120명, 삼성전자 담당자 약 50명 예상이다. 이들은 참여 규모로, 전담 인력이나 실제 투입 MM을 의미하지 않는다.

가장 큰 문제는 질의와 답변이 제원 DB에 연결되지 않아 최종 수정이 반영된 제원을 알기 어렵다는 점이다. PPT 답변, 수정 제원표 및 후속 변경 제원을 각각 확인하면서 최종본 재확인 부담이 발생한다.

## 5. 제원 추가·삭제·변경 정의안

### 5.1 비교 범위와 기본 단위

비교 범위는 **동일 PJT의 전체 제원표**이다. 기존 상태를 B, 신규 접수 상태를 N이라 하고, 건설코드로 개별 설비의 제원 묶음을 대응시킨다. 같은 설비 유형은 PRC·MODEL·MAKER로 분류하지만, 이 유형정보만으로 개별 설비의 동일성을 확정하지 않는다.

다음 정의 중 PJT 전체 범위, 미표시 전체본의 누락 코드 삭제 및 접수 즉시 반영은 사용자 확인 사항이다. 비교의 세부 정규화와 코드 변경 표시 방식은 본 문서가 제안하는 처리 정의이다.

### 5.2 설비 단위 정의

| 분류 | 판정 기준 | DB 처리 | 의미 |
|---|---|---|---|
| 추가 | N에만 건설코드가 존재 | 신규 코드의 제원 등록 | 현 PJT 데이터에 신규 대상이 생김 |
| 삭제 | B에만 건설코드가 존재 | 현재 제원에서 해당 코드 제거 | 신규 PJT 전체본에서 대상이 제외됨 |
| 변경 | 동일 코드가 양쪽에 있고 UT 추가·삭제·성상 변경 또는 제원값 차이가 있음 | 변경 상세를 구분해 반영 | 건설코드 내부의 제원 변경 |
| 유지 | 건설코드, UT 구성 및 비교 대상 제원값이 모두 같음 | 제원 내용 유지 | 실질 제원 변화 없음 |

표에서 ‘삭제’는 현재 PJT 제원 집합에서 제외된다는 뜻이다. 과거 기록을 소거하거나 실제 현장 설비가 철거됐다고 단정하는 뜻이 아니다. ‘추가’도 실제 신규 구매나 설치가 확정됐음을 의미하지 않는다.

전체본에서 기존 건설코드가 빠지면 삭제로 처리한다. 빈 건설코드, 중복 코드 또는 읽기 실패는 정상적인 누락 코드와 구분해야 한다. 전체본을 정상적으로 읽지 못한 상태를 삭제 근거로 삼지 않도록 입력 확인 절차를 구체화한다.

### 5.3 건설코드 자체가 바뀐 경우

이전 코드와 신규 코드가 동일 설비라는 사실이 확인된 경우에는 **변경 — 건설코드 변경**으로 분류하여 두 코드를 연결한다. 대응표나 확인 근거가 없으면 자동 비교의 기본값은 **기존 코드 삭제 + 신규 코드 추가**이다. PRC·MODEL·MAKER가 같아도 같은 유형의 설비가 여러 대 있을 수 있으므로 자동으로 동일 개체라고 연결하지 않는다.

선택 확장안으로 담당자가 두 코드를 동일 설비의 코드 변경이라고 확인하면 ‘코드 변경’ 관계를 추가로 기록할 수 있다. 이 기능은 제안 사항이며 현재 구현 완료로 간주하지 않는다. 원래 식별한 삭제·추가 이력과 담당자 확인 근거는 구분하여 남기는 방식으로 구체화할 수 있다.

코드 변경 관계가 확인되지 않았을 때 삭제·추가 건수를 설비의 물리적 증감 대수로 바로 사용하지 않는다. 전체 제원량 증감은 B와 N의 실제 집계값 차이로 산출하고, 이를 추가·삭제 코드 건수와 별도로 표시하는 구성을 제안한다.

### 5.4 동일 코드 내 항목의 변화

같은 코드에 속한 필드·모듈·성상·연결 항목 등에 추가·삭제·수정이 있으면 설비 단위에서는 ‘변경’으로 분류하고 항목 단위 상세 차이를 제공한다. 행 순서나 엑셀 표시 형식만 달라진 것은 실질 제원 변경과 구분하는 것이 바람직하다.

같은 코드 안의 반복 항목을 대응시키는 키, 빈 셀·0·미기재의 의미, 단위 변환 및 숫자 비교 허용 오차는 별도 규칙으로 확정한다. 이 세부 규칙은 아직 사용자 확인 또는 코드 실행 검증이 완료되지 않았다. 단순 행 위치만으로 동일 항목을 단정하지 않는 설계가 필요하다.

### 5.5 변경 표시본과 미표시 전체본

**변경 표시본:** 삭제·수정·추가 표시와 건설코드를 이용해 변경 내역을 판별한다. 삭제 표시가 된 행이 파일에 남아 있어도 현재 제원에서는 제외되어야 하므로 표시 의미를 반영하여 신규 유효 제원 집합을 구성한다. 색·기호·별도 열 등 구체적인 표시 규칙은 양식에 맞춰 정의한다.

**미표시 전체본:** 별도 변경 표시 없이 B와 N의 코드 집합 및 동일 코드의 값을 비교한다. B에만 있는 코드는 삭제, N에만 있는 코드는 추가, 공통 코드의 값 차이는 변경으로 분류한다.

두 입력 형식을 공통적인 추가·삭제·변경 내역으로 변환하여 변경량 산출과 DB 반영에 이용하는 구성을 제안한다. 현재 변경량 산출·덮어쓰기는 사용자 확인상 구현 완료이나, 위 정의의 모든 예외 처리가 이미 구현되었다는 뜻은 아니다.

## 6. 질의 결과와 최종 확인의 관계

### 6.1 개별 질의 처리

제원 항목에 질의 객체를 연결하고 동일 유형의 질의를 대공정별로 통합한다. 추천값은 명확한 기준으로 제시할 수 있는 항목에 한정한다. 담당자가 유지 또는 수정 여부를 판단하고, 수정 결과는 제원값과 변경 이력에 연결한다.

### 6.2 최종 제원 확인

사용자가 말한 결재는 기술팀 담당자가 ‘이 제원을 확인했으며 BULK 변경 제원 접수 전 최종 제원으로 인정한다’는 절차상 확인이다. 개별 변경의 반영을 허가하는 게이트나 후속 접수를 막는 잠금 절차가 아니다.

특정 시점의 제원에 대해 대공정별 확인자·확인일시·대상 범위를 기록하는 구성을 정리한다. 추가 설계안으로 해당 시점의 이력 또는 상태 식별정보를 함께 연결하면 이후 변경에도 무엇을 확인했는지 조회할 수 있다. 현재값이 바뀌었다고 과거 확인자가 신규 변경까지 확인한 것으로 표시하지 않는다.

### 6.3 별도 결재본 없이 이력 활용

사용자는 제원을 덮어써도 이전 단계로 돌아가 수정할 수 있도록 시스템을 구성하였다. 따라서 별도의 결재본 파일 복제·보관을 필수 구성으로 삼지 않고, 기존 복원 기능과 확인 시점의 관계를 이용하는 방향으로 정리한다.

별도 파일을 만들지 않는 것과 과거 상태를 전혀 보존하지 않는 것은 다르다. 복원 가능한 기록의 구체적 저장 방식, 확인 대상 시점의 보존기간, 복원 후 재수정 이력 처리 방식은 실제 구현에 맞춰 기술한다. 이력이 불변 저장되거나 모든 시점이 영구 보존된다고 단정하지 않는다.

### 6.4 즉시 반영

BULK 변경은 접수 즉시 현재 DB에 반영한다. 여기서 즉시는 별도 결재를 기다리지 않는다는 업무 의미이다. 입력 파싱과 코드·양식 등 기본 확인 없이 불완전한 값을 반영한다는 뜻은 아니다.

새 접수분 반영 후 현재 제원과 BULK 변경 전 담당자가 확인한 시점의 제원을 구분한다. REV 간 비교 화면이 아직 없어도 기존 단계 복원 기능과 후속 REV 비교 기능은 별개로 설명한다.

## 7. 검토·추천 사례

**유량:** 폐수·WATER·B.GAS에 대해 전자 및 삼우설계와 협의된 노즐 사이즈별 유량표를 참조한다. 해당 값은 강제 한도가 아닌 추천·검토 기준이다. 초과만으로 반영이나 최종 확인을 차단하지 않고 실제 요구량을 검토하여 유지·수정을 판단한다. 실제 사용보다 크게 기재된 유량이 여러 개 누적될 때 배관 규모 확대의 비효율을 검토할 수 있다. 배관·공사비 절감 효과는 별도 실측 전이다.

**전기:** 제원표의 피상전력과 전압·전류 기준 계산값의 불일치를 검토한다. 전원 구성·단위·허용 오차·수정 대상의 실제 규칙은 추가 구체화한다.

**GCS:** IGPM 자재명과 DS-EHS 제원 자재명을 연결한다. H2SO4와 H2SO4 1% 같은 표기 차이를 검토하되, 원본명과 농도 보존 방식은 아직 미확정이다. 농도 삭제를 자동 추천의 기본으로 삼지 않는다.

## 8. 처리 흐름

제원 입력 → 건설코드별 DB 저장 → 검토 대상 식별 및 추천값 제공 → 동일 유형 질의의 대공정별 통합 처리 → 제원 반영·변경 이력 연결 → BULK 변경 전 특정 시점에 대공정 담당자 최종 확인 → 후속 PJT 전체 변경자료 접수 → 표시 유무에 따른 변경 식별 → 변경량 산출 및 현재 DB 즉시 반영 → 필요 시 이전 상태 조회·복원·수정.

확인 대상 시점과 이력을 연결하는 부분, 두 입력 형식의 상세 정규화 및 코드변경 확인 관계는 문서에서 구체화한 설계안이다.

## 9. 발명의 효과 — 제출 본문 초안

종래에는 설계사가 PPT 질의 패키지를 반복 발행하고 제조 기술팀과 답변·재질의를 주고받아, 최초 검토 약 1주와 별도로 질의 과정에 약 2개월이 소요된다. 또한 질의 결과와 제원 데이터가 연결되지 않아 최종 수정이 반영된 제원을 식별하기 어렵다.

본 발명은 제원 항목과 질의·답변·변경 이력을 DB로 연결하고 동일 유형 질의를 대공정별로 통합하여, 반복 자료 작성·답변 왕복·수정 반영 확인의 부담을 줄인다. BULK 변경 전의 특정 시점에 기술팀 담당자의 최종 확인 이력을 남겨, 확인 주체와 대상 시점이 연결된 기준 제원을 조회할 수 있다.

추가·삭제·변경 표시가 있는 자료와 표시 없는 PJT 전체자료를 건설코드 기준으로 처리하여 변경량을 산출하고, 접수 즉시 현재 DB에 반영한다. 이전 상태의 복원 기능을 활용하여 과거 제원과 수정 근거를 추적하고 정정할 수 있어, 파일별 최종본 재확인과 대량 변경 취합의 부담을 줄일 수 있다.

축적된 데이터는 신축 및 리트로핏의 변경 검토에 재사용할 수 있으며, 향후 REV 비교·PJT 총량 비교 및 자동설계 지원의 기반이 된다.

- **DB 신뢰성:** 질의 결과와 현재값의 일치, 최종 확인 시점 조회, 변경 반영 후 이전 상태 복원 가능 여부를 시험한다.

- **유량 검토:** 초과 검토 중 실제 수정과 유지 판단을 구분한다. 기준 초과를 모두 오류 수정 실적으로 집계하지 않는다.

## 15. 질의 수정분과 신규 변경의 구분 — 추가 설계안

### 15.1 특허 본문용 간단 정의

설비 단위의 추가·삭제는 건설코드의 신규 발생 또는 소멸로 구분한다. 건설코드가 유지된 상태에서 UT 추가·삭제·성상 변경 또는 제원값 변동이 발생하면 설비 단위의 변경으로 분류하고 세부 내역을 기록한다. 건설코드와 UT 구성 및 관리 대상 제원값이 모두 같으면 유지로 분류한다. 동일 설비의 건설코드 변경이 확인되면 변경으로 관리하되, 대응 관계가 불명확하면 삭제·추가 후보로 관리한다.

### 15.2 문제: 비교 기준의 불일치

변경 전 최종 제원과 신규 접수본의 두 값만 비교하면, 신규 접수본에 과거 질의 수정 결과가 반영되지 않은 경우 이를 신규 변경으로 인식할 수 있다. 반대로 이전 접수 원본만 비교 기준으로 사용하면 질의로 확정한 값이 신규 전체본의 예전 값으로 되돌아갈 수 있다.

예를 들어 최초 접수 유량 100을 질의로 60으로 확정했는데, 후속 전체본에 100이 남아 있으면 단순 비교는 60→100을 변경으로 집계한다. 이 차이가 과거 수정의 반영 누락인지 의도적인 100으로의 재변경인지는 값만으로 확정할 수 없다.

### 15.3 비교에 필요한 세 가지 상태

- B: 신규 변경자료가 작성될 때 기반으로 사용한 접수 제원의 상태.
- Q: 질의 처리 결과를 반영하고 담당자가 최종 확인한 제원의 상태.
- N: 새로 접수한 변경 제원의 상태.

B는 무조건 최초 접수본을 뜻하지 않는다. 공급자가 신규 자료를 어느 REV를 기준으로 작성했는지 확인하여 해당 상태를 지정해야 한다. B가 확인되지 않으면 분류의 확실성도 낮아진다. Q와 질의 이력은 기존 복원 기능으로 참조하는 방향이며 별도 파일 복제를 필수로 삼지 않는다. 비교에 필요한 시점이 실제로 복원 가능한지는 구현 확인이 필요하다.

### 15.4 항목별 비교 규칙

| 비교 조건 | 해석 | 제안하는 처리 |
|---|---|---|
| B=Q=N | 변화 없음 | 유지 |
| B≠Q, N=Q | 질의 확정값이 신규본에도 반영됨 | 질의 반영 완료, 신규 변경으로 중복 집계하지 않음 |
| B≠Q, N=B | 신규본에 질의 수정이 미반영되었거나 과거값으로 되돌리는 변경일 수 있음 | 질의 미반영·되돌림 확인 대상으로 분리, 자동 신규 변경 확정에서 제외 |
| B=Q, N≠B | 기존 질의 수정과 충돌하지 않는 값 차이 | 신규 변경 후보로 분류 |
| B≠Q이고 N이 B·Q 모두와 다름 | 질의 확정값과 신규값의 충돌 | 충돌 대상으로 분리하고 변경 근거 확인 |

이 규칙은 자동 분류 보조안이다. N=B인 경우를 무조건 질의 미반영으로 삭제해서는 안 된다. 실제로 이전값으로 되돌리려는 요청일 수 있으므로 표시된 변경 지시 또는 담당자 확인을 근거로 확정한다. B=Q에서 신규 차이가 난 경우에도 데이터 정확성을 보장하는 의미는 아니다.

### 15.5 UT 추가·삭제에도 같은 원리 적용

질의로 삭제한 UT가 새 전체본에 다시 등장하거나, 질의로 추가한 UT가 새 전체본에서 빠졌다면 해당 질의 이력과 대조하여 재추가·재삭제 의도인지 과거 수정 미반영인지 확인 대상으로 분리한다. 건설코드 변경으로 항목 대응이 불명확한 경우에도 자동 연결하지 않고 후보로 표시한다.

### 15.6 즉시 반영 및 변경량 산출의 경계

기존 운영 구상은 변경 접수 즉시 현재 DB에 반영하는 것이다. 다음은 이번 우려를 해결하기 위한 **정책 제안**이며 사용자 확정 또는 구현 완료 사항이 아니다.

신규 접수 원본과 접수 이력은 즉시 등록하고, 확실한 변경은 기존 방침대로 현재 제원에 반영한다. 질의 미반영·되돌림·충돌 후보는 별도 표시하여 기존 확정값을 자동으로 덮어쓰지 않는 방안을 권장한다. 이는 모든 변경에 새 결재 단계를 추가하는 것이 아니라 이력이 충돌하는 항목만 예외로 다루는 설계이다. 현재값 반영을 보류하는 예외 정책은 사용자와 최종 확정한다.

신규 접수 원본의 차이, 질의 미반영·충돌 후보, 실제 현재 제원에 반영된 변경을 구분하여 집계한다. 변경량은 비교 기준의 식별정보 및 반영 상태와 함께 제공하고, 미확정 후보를 실제 확정 변경량으로 합산하지 않는다.

### 15.7 특허 설명용 추가 문구

본 시스템은 신규 변경 제원과 질의 반영 후 제원 간의 단순 차이뿐 아니라, 신규 변경자료의 기반 제원 및 질의 수정 이력을 함께 참조하여 차이를 분류한다. 이에 따라 질의 확정값이 반영되지 않은 항목, 신규 변경 후보 및 상충 항목을 구분하고, 과거 질의 수정 결과를 신규 변경으로 중복 집계하거나 미반영된 과거값으로 덮어쓰는 것을 줄일 수 있다.

본 절은 문제를 해결하기 위해 추가 제안한 기술 구성으로, 기존 데모에서 구현·시험되었다고 주장하지 않는다. 선행기술 대비 차별성이나 권리성이 확인되었다는 의미도 아니다.

## 18. 발명의 우선순위 및 GCS 양방향 정합성 검증 후보

### 18.1 첫 번째 중심: 질의 결과의 실제 최종 반영 확인

사용자는 본 플랫폼의 가장 중요한 차별점을 ‘제원 질의 이후 최종 반영 여부를 알 수 있음’으로 재확인하였다. 따라서 변경 비교 알고리즘 자체보다 **질의 대상·확정한 처리 결과·실제 DB 반영값·최종 확인 시점을 연결하여 답변 완료와 실제 반영 완료를 구분하는 구조**를 발명의 첫 번째 중심으로 유지한다. 이 연결의 기술적 차별성은 앞선 문헌과 추가 대조해야 한다.

### 18.2 두 번째 후보: 케미컬·슬러리와 폐액 제원의 양방향 정합성 검증

사용자는 정해진 케미컬·슬러리에 따라 배출 폐액 성상의 대응관계가 있으며, 폐액 측에서도 해당 공급 자재와의 대응을 확인하는 구상을 제시하였다. 이는 자재명 표준화와 구분되는 공급·배출 제원 간 정합성 검증 후보이다. 규칙과 적용 단위는 아직 미확인이다.

제안 처리 흐름은 다음과 같다.

1. 같은 장비의 공급 케미컬·슬러리와 폐액 제원을 연결하여 장비 단위로 정합성을 검증한다. 이는 2026-10-22 사용자 확인 사항이다. PRC·MODEL·MAKER가 같은 다른 장비의 자재를 해당 장비의 공급 자재로 대신 대조하지 않는다.
2. 사내 기준의 자재 식별정보와 입력 명칭을 대응시킨다. 농도·등급·공정조건 등 기준에 영향을 미치는 속성은 실제 규칙에 따라 보존한다.
3. 공급 자재를 출발점으로 필요한 폐액 제원의 누락과 부적합 연결 후보를 검사한다.
4. 등록된 폐액을 출발점으로 이를 설명하는 공급 자재·공정조건이 존재하는지 역방향 검사한다.
5. 일치·누락·불일치 후보를 구분하고 동일 유형을 대공정별 질의로 통합한다.
6. 질의 결과가 반영되면 양쪽 제원을 다시 검사하여 실제 반영 및 정합성 회복 여부를 연결해 제공한다.

정방향 매핑을 단순 뒤집어 하나의 자재를 확정하는 방식으로 전제하지 않는다. 하나의 폐액에 복수 공급 자재가 대응하거나 여러 자재·공정조건의 조합이 필요한 경우에는 후보 집합·조건 관계로 관리한다. ‘발생해야 하는 폐액’과 ‘연결이 허용되는 폐액’도 규칙에서 구분해야 한다. 후자는 모든 허용 폐액의 존재를 요구하는 규칙이 아니다.

사용자는 **복수 자재가 하나의 폐액에 대응할 수 있음**을 확인하였다. 역방향 검사는 등록 폐액에 대응 가능한 자재 집합과 해당 장비의 실제 등록 자재를 대조하는 방식으로 구체화한다. 집합 내 자재 중 하나만 있으면 되는지, 복수 자재가 함께 있어야 하는지는 실제 매핑 규칙을 받은 뒤 정한다. 구체적 사례 및 현재 구현 여부는 사용자 추후 코멘트 대기 상태로 둔다.

### 18.3 선행기술과 판단 경계

공개된 반도체 폐수 특허에서 CMP 공정·슬러리와 발생 폐수의 관계를 설명하고 있으며, 폐기물 속성·관계 DB에 기반한 호환성 판단 및 화학공정 정보에 따른 폐기물 발생원 분석의 선행자료도 검색되었다. 따라서 ‘공급 화학물질과 폐액은 관련된다’ 또는 ‘규칙표를 조회한다’는 넓은 아이디어가 삼성전자에만 알려진 것이라고 단정하지 않는다.

- [EP1078887A1](https://patents.google.com/patent/EP1078887A1/en): CMP 공정과 관련 폐수 처리. 공보 검색 결과의 설명 확인이며 본 플랫폼의 양방향 제원 검증을 개시한 것으로 판정하지 않음.

- [Systematic Waste Minimization in Chemical Processes. 2. Intelligent Decision Support System](https://pubs.acs.org/doi/10.1021/ie0102089): 공정·화학·자재 정보를 이용한 폐기물 및 발생원 분석을 설명하는 출판사 초록 확인. 전문은 접근 제한으로 미열람.

사내 실제 매핑표의 독점성·비공개성은 확인 전이다. 사내 데이터의 고유한 가치와 검증 방법의 신규성·진보성은 구분하여 검토한다. 실제 표 전체를 문서에 수록하는 것을 전제하지 않고 우선 익명화한 사례와 규칙 구조로 고안을 정리한다. 출원 명세서에는 실시 가능한 설명이 요구되므로 공개 범위는 사내 특허 담당자와 정한다.
