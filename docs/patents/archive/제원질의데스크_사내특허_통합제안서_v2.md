# 제원 질의 데스크 — 사내 특허 통합 제안서 v2

작성일: 2026-10-21 | 용도: 사내 발명제안 검토 및 사용자 질의

## 1. 통합 방향

사용자가 제공한 「제원질의데스크_특허제안서_클로드 최신.txt」의 질의 이력 재사용·자동전환 구조와 기존 「제원관리_특허초안.md」의 대공정별 일괄 승인·셀 반영·재검증 구조를 통합하였다. 사용자가 강조한 도입 전후 비교를 앞에 두고, 효과를 만드는 구체적인 데이터 처리 구조를 연결하였다. 삼성전자 내부 양식이나 심사 기준 문서는 제공받지 않았으므로 본 문서가 공식 양식과 일치한다고 전제하지 않는다.

클로드 문서에서 구현되었다고 서술한 기능 중 일부는 GitHub의 demo/spec-qa-workflow.html에서도 코드로 확인하였다. 서버 구현과 경량 웹 구현은 서로 다른 구현체이며, 모든 기능이 하나의 운영 시스템에서 함께 검증되었다는 의미는 아니다. 실제 업무 절차와 운영 효과는 사용자 답변 후 확정한다.

## 2. 발명의 명칭

설비 유형별 제원 질의 처리 이력에 기초한 자동 질의 생성 및 통합 승인 방법 및 시스템

## 3. 제안 요지

동일 유형의 설비에 대해 과거에 확정한 제원값이 있어도, 프로젝트와 건설코드가 바뀔 때마다 질의·답변·수정 업무를 다시 수행하는 문제를 해결하고자 한다.

설비 식별정보와 설비모듈·질의 대상 항목을 조합한 유형키로 확정 이력을 축적하고, 반복 처리된 유형의 후속 제원 항목을 탐지하여 제안값이 포함된 질의를 자동으로 생성한다. 동일 승인 범위의 대상들을 하나의 질의로 묶고, 담당자의 승인 후 연결된 항목을 갱신한다. 변경 이력과 반영 후 재검증을 연결한다.

이에 따라 반복 업무를 ‘매번 질문을 작성하고 값을 새로 판단하는 절차’에서 ‘과거 확정값을 검토하고 승인하는 절차’로 전환하는 것이 핵심이다. 여기서 자동전환은 질의 생성·값 제안의 자동화를 뜻하며, 담당자 승인 없는 무조건적인 제원 변경을 뜻하지 않는다.

아래 도입 전은 클로드 초안에 기술된 상황을 바탕으로 한 확인 전 가정이다. 실제로 이미 수행 중인 자동화가 있다면 해당 항목을 수정한다.

### 두 가지 비교 기준

비교 A는 현행 수작업 업무와 통합 플랫폼을 비교한다. 파일 취합, 질의, 승인, 수정, 재검증까지 전체 업무시간의 차이를 보여준다.

비교 B는 이미 존재하는 규칙 기반 플랫폼과 이력 활용 기능을 비교한다. 동일한 반복 사안에 대해 수동 질의를 계속 등록하는 경우와, 유형 이력에 따라 자동으로 질의를 생성하는 경우를 비교한다. 이 비교가 이력 활용 기능의 추가 효과를 분리해 설명한다.

둘을 섞어 기존 플랫폼에서 이미 얻은 효과를 이력 활용 기능만의 효과로 계산하지 않는다.

## 5. 종래 문제 → 해결수단 → 효과

### 5.1 반복 판단을 반복 확인으로 전환

종래에는 장비의 건설코드나 프로젝트가 바뀌면 과거 동일 설비 유형의 확정 결과를 찾아 연결하기 어려워 같은 질문과 답변이 반복된다. 본 발명은 대공정, PRC, 모델, 제조사, 설비모듈 및 항목으로 구성된 유형키로 확정 결과를 조회한다. 유형이 반복 처리되면 후속 항목에 제안값이 포함된 질의를 생성한다. 이로써 과거 결론 탐색, 질의 작성 및 반복 답변의 부담을 줄일 수 있다.

단, 동일한 유형키가 동일한 설계 조건을 뜻하는지 확인해야 한다. 공급 조건·성상·용량·설비 버전 등으로 값이 달라지는 경우 해당 조건을 유형키 또는 적용 조건에 반영하는 확장이 필요하다.

### 5.2 개별 승인에서 범위별 통합 승인으로 전환

동일한 수정이 여러 장비에 필요해도 개별 질의로 만들면 승인 수가 증가한다. 본 발명은 동일 프로젝트·대공정 및 동일 수정 조건의 대상을 묶고, 질의 하나에 복수 셀을 연결한다. 이에 따라 승인 대상 수와 수동 입력을 줄일 수 있다. 대공정을 묶음 조건에 넣어 승인 범위가 다른 대상의 혼합을 줄인다.

서버 규칙 기반 구현은 대공정·규칙·세부항목·제안값으로 묶는다. 경량 웹의 패턴 기반 구현은 프로젝트·대공정·항목·제안값·PRC·모델·제조사·설비모듈로 묶는다. 프로젝트를 넘어 이력을 재사용하는 것과, 서로 다른 프로젝트의 대상을 한 번에 승인하는 것은 구분한다.

### 5.3 질의 완료와 데이터 변경의 연결

답변 완료와 실제 파일 수정이 분리되면 일부 대상에 값이 반영되지 않을 수 있다. 본 발명은 질의에 연결된 대상에 승인값을 적용하고 변경 전후 값을 기록한다. 변경 후 제원표 재검증까지 연결하여 데이터와 검증 상태의 불일치를 줄인다.

검증은 등록된 규칙 범위에서만 수행된다. 모든 공학적 적합성이나 모든 오류의 제거를 보장하는 효과로 표현하지 않는다.

## 6. 핵심 처리 구성

1. **입력 및 식별:** 제원표에서 실제 설비 식별정보와 설비모듈·제원 항목을 추출한다.
2. **이력 확정:** 질의의 승인값이 실제 제원에 반영된 경우 대상별 확정값·처리방식·시점·건설코드·프로젝트를 기록한다.
3. **유형별 집약:** 동일 유형키의 패턴 데이터를 갱신하고 제안값을 산출한다.
4. **자동전환 판단:** 수동 처리 이력이 설정 기준에 도달한 유형에 자동 질의 생성 상태를 부여한다.
5. **후속 항목 탐지:** 동일 유형키를 가지면서 제안값과 다른 신규 항목을 찾고, 기존 질의 대상과의 중복 여부를 확인한다.
6. **질의 생성 및 묶음:** 승인 범위와 수정 조건별로 복수 대상을 묶어 제안값을 가진 질의를 생성한다.
7. **검토 및 반영:** 권한자의 승인 후 연결된 대상 셀을 갱신하고 변경 이력을 기록한다.
8. **재검증:** 변경 제원표를 다시 검증하고 검증 결과·처리 상태를 갱신한다.

현재 경량 웹 코드에는 수동 처리 이력 기준 3건, 최근 발생 이력 보관 상한 15건이 들어 있다. 이는 확인된 구현값이며 실제 현장의 적정 기준으로 확정된 값은 아니다.

## 7. 도입 전후 실시예

실제 사례를 받기 전까지 아래는 작동 설명용 가정이다.

**상황:** 프로젝트 A에서 동일 설비 유형의 특정 제원 항목을 기술팀과 설계사가 반복 검토하여 값 V로 확정하였다. 프로젝트 B에서 같은 조건의 설비에 다른 값 W가 들어왔다.

**도입 전:** 설계사가 차이를 발견하고 질의를 작성한다. 기술팀은 과거 사례를 찾거나 다시 검토하여 답변한다. 설계사 확인 후 수정값을 제안하고 최종 승인 및 파일 반영을 진행한다.

**도입 후:** 시스템은 프로젝트 B의 항목과 과거 확정 이력의 유형키를 비교한다. 자동전환된 유형이고 현재값 W가 제안값 V와 다르면 제안값과 근거 이력이 연결된 질의를 생성한다. 동일 승인 범위의 대상은 묶고, 담당자가 적합성을 확인하여 승인한 후 값을 반영한다. 반영 이력과 재검증 결과를 남긴다.

**효과:** 질문 작성·사례 검색·반복 답변을 줄이며, 여러 대상의 승인과 반영을 연결한다. V가 현 조건에 적절하지 않으면 담당자가 반려 또는 새 값을 제안할 수 있어야 한다. 다른 조건을 가진 항목에 과거값을 그대로 적용하지 않도록 적용 조건을 확정하는 것이 중요하다.

## 8. 효과 측정 계획

| 지표 | 도입 전 측정 | 도입 후 측정 | 산정 방법 |
|---|---|---|---|
| 총 작업시간 | 탐색·질의 작성·답변·승인·입력·재확인 시간 | 제안 검토·승인·예외 처리·재확인 시간 | (전-후)/전 × 100% |
| 수동 질의 수 | 사람이 등록한 질의 수 | 자동 생성 후 남은 수동 등록 수 | 동일 데이터·동일 범위 비교 |
| 반복 답변 횟수 | 동일 유형에 새로 작성한 답변 수 | 제안값 확인 외 새 답변이 필요한 수 | 유형별 비교 |
| 승인 객체 수 | 개별 승인 질의 수 | 묶음 승인 질의 수 | 동일 대상 셀 수 기준 비교 |
| 수정 반영 누락 | 승인 대상 중 미반영 셀 수 | 동일 정의의 미반영 셀 수 | 승인 셀 수를 분모로 비교 |
| 제안 채택률 | 해당 없음 또는 수동 제안 기준 | 승인된 제안/검토된 전체 제안 | 반려·수정 제안도 함께 기록 |
| 재사용 범위 | 과거 처리 결과를 참조한 프로젝트 수 | 유형 이력이 활용된 프로젝트 수 | 프로젝트별 실제 사용 근거 확인 |

예컨대 100개 대상이 5개 질의로 묶였다면 승인 객체 수는 95% 감소한다. 이는 작업시간·인건비·오류가 95% 감소했다는 뜻이 아니다. 실제 절감 수치는 사용자 데이터 확보 후 기입한다.

## 9. 청구범위 검토용 통합 초안

아래는 기술 구성을 정리하기 위한 작업 초안이다. 선행기술 조사에 따른 신규성·진보성 판단 및 출원용 청구범위 검토는 수행하지 않았다.

### 청구항 1 — 이력 기반 자동 질의 생성 방법

컴퓨터에 의해 수행되는 반도체 제조설비의 제원 질의 처리 방법에 있어서,

설비 식별정보, 설비모듈 식별정보 및 제원 대상 항목을 조합한 질의유형 식별키를 생성하는 단계;

상기 질의유형 식별키에 대응하여 질의 처리 후 실제 제원에 반영된 확정값 및 수동 또는 자동 처리 여부를 포함하는 처리 이력을 저장하는 단계;

상기 처리 이력에 기초하여 상기 질의유형의 제안값을 산출하고, 수동 처리 이력이 미리 정한 기준에 도달한 질의유형을 자동 질의 생성 대상으로 설정하는 단계;

후속 제원 데이터에서 상기 자동 질의 생성 대상과 동일한 질의유형 식별키를 가지면서 상기 제안값과 다른 값을 갖는 항목을 탐지하는 단계; 및

상기 탐지된 항목에 대하여 사용자의 개별 질의 등록 요청 없이 상기 제안값을 포함하는 질의를 생성하는 단계;

를 포함하는 제원 질의 처리 방법.

### 청구항 2

청구항 1에 있어서, 상기 설비 식별정보는 대공정, 설비 버전 또는 공정 구분을 나타내는 PRC, 모델 및 제조사 정보를 포함하고, 서로 다른 프로젝트 또는 건설코드의 항목에 대해 동일한 질의유형 식별키에 대응하는 처리 이력을 조회하는 방법. 단, PRC의 실제 의미는 사용자 확인 후 문언을 확정한다.

### 청구항 3

청구항 1에 있어서, 자동 생성 대상의 설정 여부를 판단하는 이력에서 자동 처리 이력을 수동 처리 건수로 집계하지 않는 방법.

### 청구항 4

청구항 1에 있어서, 자동 생성된 질의의 대상을 프로젝트, 대공정 및 제안값을 포함하는 승인 범위별로 분류하여, 하나의 질의에 복수 제원 항목을 연결하는 방법.

### 청구항 5

청구항 4에 있어서, 상기 대공정에 대한 사용자 권한 확인 및 승인에 응답하여 상기 복수 제원 항목을 갱신하고, 항목별 변경 전후 값과 상기 질의를 연결하는 이력을 저장하는 방법.

### 청구항 6

청구항 5에 있어서, 갱신된 제원 항목이 속하는 제원표를 식별하고 검증 규칙을 재적용하여 검증 결과를 갱신하는 방법.

### 청구항 7

청구항 1에 있어서, 질의유형별로 보관되는 최근 처리 이력 수를 제한하고 해당 이력에 기초하여 제안값을 산출하는 방법.

### 청구항 8

청구항 1에 있어서, 제안값의 반영 전에 적용 가능한 검증 규칙으로 후보값을 검증하고 오류 기준을 위반하는 경우 반영을 차단하는 방법. 이 항은 통합 설계의 구성안으로, 모든 경로에 대한 공통 게이트 구현이 확인된 것으로 표현하지 않는다.

### 청구항 9

청구항 1에 있어서, 사용자가 수동 질의를 등록할 때 대상 항목이 자동 질의 생성 대상으로 설정되어 있으면, 해당 질의를 제안값이 포함된 자동 질의로 전환하는 방법.

### 청구항 10 — 시스템

프로세서 및 명령어를 저장하는 메모리를 포함하고, 상기 명령어는 상기 프로세서에 의해 실행될 때 청구항 1의 방법을 수행하도록 구성되는 제원 질의 처리 시스템.

별도 검토할 청구 축: 기존 초안의 ‘규칙 기반 교정 후보를 대공정별로 묶고 승인·반영·재검증하는 방법’은 이력 자동전환이 없는 경우에도 설명 가능한 구성이다. 이력 활용과 함께 출원할지 분리할지는 실제 차별점과 선행기술 검토 후 결정한다.

## 10. 원문 표현의 조정 및 확인 결과

| 원문 주장 또는 쟁점 | 통합본의 처리 |
|---|---|
| 이력 학습이 아직 구현되지 않았다는 기존 초안 설명 | 서버만 확인했던 범위를 보완. 경량 웹 코드에서 패턴 집약·자동전환·능동 생성 확인 |
| 저장량이 질의 수에 따라 증가하지 않음 | 패턴 문서 수와 최근 이력 보관량에 한정. 전체 질의·교정·버전 데이터 저장량은 별도 증가 가능 |
| 동일 판단이 3회 반복되면 자동전환 | 코드상 최근 최대 15개 이력 중 MANUAL 발생 수 3개가 기준. 확정값 3개가 서로 같아야 한다는 조건은 확인되지 않음 |
| 한 번에 묶은 다수 셀은 독립된 판단의 반복 | 코드상 대상별 이력이 추가되므로 동일 질의의 여러 셀이 여러 발생으로 집계될 수 있음. 독립 질의·설비·프로젝트 기준 여부 질의 필요 |
| 최빈값 동률이면 항상 최신값 선택 | 코드 주석과 달리 구현상 항상 최신값임을 보장하지 않아 단정 제외 |
| 자동전환은 이력 감소 시 해제 | 코드는 한번 자동전환되면 상태를 유지. 해제·유효기간 정책은 확인 필요 |
| 모든 자동·수동 반영 전 공통 검증 게이트 완성 | 서버 수동 후보값 검증은 확인. 경량 웹 자동 승인 경로 전부에 공통 사전 검증이 적용된다는 주장은 보류 |
| 건설코드로 누락된 실제 설비 식별정보 복원 | 코드의 결정론적 시험값 생성과 구분. 실제 제조사·모델 복원 효과로 사용하지 않음 |
| PRC는 공정코드 | README의 장비 버전 설명과 클로드의 공정코드 설명이 달라 사용자 확인 전 확정하지 않음 |
| 사용하면 자동 처리율·정확도가 반드시 향상 | 자동전환 대상 확대 가능성으로 표현. 채택률과 정확도 향상은 실측 필요 |
| 발명자 및 조직 기재 | 미확인 상태 유지. 문서의 체크 표시를 실제 답변으로 간주하지 않음 |

## 11. 사용자 확인 질의

답변은 아래 번호에 맞춰 짧게 주셔도 된다. 모르는 수치는 ‘미측정’, 아직 정하지 않은 정책은 ‘미정’으로 표시한다. 사번이나 개인 연락처는 현재 기술 내용을 정리하는 데 필요하지 않다.

### 우선 확인할 7가지

**Q1. 실제 도입 전 절차는 무엇인가?**
제원표를 어디서 받아 누가 검토하고, 질의는 메일·엑셀·별도 시스템 중 어디서 주고받으며, 최종 수정은 누가 어떤 파일에 반영하는가? 실제 순서대로 알려 달라. 규칙 기반 검증이나 과거 질의 검색이 이미 가능한지도 포함한다.

**Q2. 실제 반복 질의 사례 한 건은 무엇인가?**
설비 유형·모듈 / 문제 항목 / 기존 입력 / 기술팀의 최종 판단 / 다른 장비나 프로젝트에서 반복된 상황을 알려 달라. 명칭·값은 익명화해도 된다. ‘성상 표기 교정’ 외에 사람의 기술 판단을 반복하는 대표 사례가 특히 필요하다.

**Q3. 동일 설비 유형을 판단하는 필수 조건은 무엇인가?**
대공정+PRC+모델+제조사+모듈+항목이면 충분한가? 성상, 용량, 압력, 운전조건, 설비 옵션, 사이트·프로젝트별 기준 등이 달라지면 같은 모델도 값이 달라지는가? PRC는 실제로 장비 버전인가, 공정코드인가?

**Q4. 무엇이 몇 번 반복되어야 자동 질의를 생성해도 되는가?**
예: ‘같은 확정값을 서로 다른 질의 3건에서 승인’, ‘서로 다른 장비 3대’, ‘프로젝트 2개 이상에서 반복’. 한 묶음의 셀 100개를 100회로 볼지 1회로 볼지도 필요하다. 확정값이 서로 다를 때 제안을 중지할지, 최빈값을 제시할지 알려 달라. 담당자 최종 승인은 계속 필요한지도 확인한다.

**Q5. 규모와 소요시간은 어느 정도인가?**
프로젝트당 장비·제원표 수 / 월 또는 프로젝트당 질의 수 / 반복 질의 비중 / 질의 1건의 실제 작업시간 / 답변 대기를 포함한 경과시간 중 아는 것만 알려 달라. 도입 후 시험값이 있는지도 포함한다. 추정치라면 추정으로 표시한다.

**Q6. 현재 어느 단계이며 어떤 기능을 시험했는가?**
아이디어·로컬 데모·사내 시험·실제 운영 중 어느 단계인가? 서버 버전과 경량 웹 버전 중 실제 사용할 것은 무엇인가? 유형 이력 축적→자동 질의 생성→승인→반영까지 직접 확인했는가? 사용자만 알고 있는 더 최신 코드가 있는가?

**Q7. 가장 강조할 현장 손실과 제출 형식은 무엇인가?**
반복 질의 시간 / 담당자 승인 병목 / 제원 반영 누락 / 프로젝트 간 판단 불일치 / 설계 재작업 중 중요도 1·2순위를 알려 달라. 사내 제안서의 항목명·분량 또는 양식이 있으면 그 구조에 맞춘다.

### 후속 확인 3가지

Q8. 제안값이 반려되거나 기준이 변경되면 자동전환을 해제해야 하는가? 과거값의 유효기간, 적용 제외 조건, 규칙 변경 시 재검증 정책이 있는가?

Q9. GitHub에 공개된 범위와 최초 공개일은 언제이며, 사내 시험·발표·외부 공유 이력은 무엇인가? 현재 저장소 공개 여부와 별개로 실제 공개 경위를 확인한다.

Q10. 유사한 사내 시스템이나 기존 출원으로 알고 있는 것이 있는가? 발명 아이디어별 기여자와 최초 구체화 시점은 후속으로 정리한다.
